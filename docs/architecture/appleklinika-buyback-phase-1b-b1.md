# Apple Klinika Buyback Phase 1B-B1

Status: implemented, awaiting acceptance

Date: 2026-07-15

## Scope

Phase 1B-B1 connects the accepted pure domain model to the existing Phase 1A WordPress tables. It adds an internal WordPress repository, row mapper, transaction manager, UTC clock, request-number generator, transactional status-event store, minimal create/transition handlers, and a real MariaDB integration suite.

Plugin version is `0.3.0`. The code and installed database schema remain `1.0.0`; this phase contains no migration or table change.

## Schema compatibility completion

The request table has four required fields that Phase 1B-A could not represent. The domain now includes immutable `DeviceCategory`, `ModelKey`, `DeviceDisplayName`, and `RequestSource` value objects. V1 permits the `iphone` category; request sources are explicit `native`, `legacy_user_meta`, or `qa_fixture` values. Production callers must choose their source and never receive an implicit QA source.

`BuybackRequest` also retains an optional typed `LegacyReference`. The QA `demo_marker` is deliberately not part of business state; it is accepted only by the internal creation DTO and exists to guarantee integration-test cleanup.

## Identity and repository behavior

The repository port now has a type-safe `insert(NewBuybackRequest): BuybackRequest` method. The DTO contains validated domain values but no database identity. `WordPressBuybackRequestRepository` inserts the row, reads `$wpdb->insert_id`, creates a positive `BuybackRequestId`, and reloads a complete aggregate through `WordPressBuybackRequestMapper`.

No `MAX(id)`, manual `AUTO_INCREMENT` inspection, reservation, or public ID leakage is used. Duplicate request numbers and legacy references fail with `DuplicateBuybackRequestException`. The unique database index remains the final concurrency authority: if another process wins after the generator's availability check, the insert path converts the resulting duplicate into the same typed exception so the application caller may retry safely.

Implemented repository operations:

- insert and fully reconstitute a draft;
- nullable lookup by typed request ID or unique request number;
- indexed request-number and legacy-reference existence checks;
- typed customer and status pages with `updated_at`, `created_at`, then `id` descending order;
- expected-version save with a two-column `id`/`version` predicate.

The application transition handler turns a missing nullable lookup into `BuybackRequestNotFoundException`. An update affecting no rows reloads the identity: no row means not found, while a different version means `StaleAggregateVersionException`. Stale writes are never retried automatically.

## Transactions and events

`WordPressTransactionManager` explicitly issues `START TRANSACTION`, `COMMIT`, and `ROLLBACK` on the existing `$wpdb` connection. Nested transactions are rejected. Every throwable is rethrown after rollback and the manager always clears its in-process active flag.

`TransitionBuybackRequestHandler` loads and version-checks the aggregate, invokes `StatusTransitionPolicy`, saves the new version, and persists pending `BuybackStatusChanged` events inside one transaction. Events are released from the in-memory aggregate only after commit.

`WordPressDomainEventStore` writes `buyback_status_changed` rows. Its SHA-256 idempotency key is derived from request ID, accepted aggregate version, transition statuses, actor, UTC event time, correlation ID, and canonical scalar metadata. Exact retries are resolved only by the idempotency-key unique index through a no-op `ON DUPLICATE KEY UPDATE`; unrelated SQL failures remain failures. A different aggregate version or event receives a different key. Empty correlation IDs remain SQL `NULL`; the private payload contains only safe technical metadata such as aggregate version, and obvious customer-sensitive metadata keys are rejected.

The final acceptance review corrected two local persistence details without changing the schema: aggregate version is now part of event identity, and broad `INSERT IGNORE` handling was replaced so malformed or unrelated database failures cannot be mistaken for idempotent success.

## Request numbers and time

`WordPressRequestNumberGenerator` uses:

```text
AKB-YYYYMMDD-XXXXXX
```

The date comes from the injected UTC clock and the six uppercase hexadecimal characters come from three cryptographically secure random bytes. The generator checks the unique repository index, retries at most five times by default, and throws `RequestNumberGenerationException` after bounded exhaustion.

`SystemClock` returns `DateTimeImmutable` in explicit UTC. The mapper converts every stored/reconstituted request and event timestamp to UTC without changing WordPress site timezone settings.

## Internal handlers

- `CreateDraftBuybackRequestHandler` generates the public request number, obtains UTC time, builds the internal insertion DTO, and inserts it transactionally.
- `TransitionBuybackRequestHandler` performs typed not-found/version checks and commits state plus event atomically.

Neither handler is registered through HTTP, REST, AJAX, shortcode, admin mutation UI, account endpoints, or WP-CLI.

## Integration verification

Run:

```bash
make test-buyback-persistence
```

The suite boots the real local WordPress/MariaDB stack and verifies generated identity, complete round-trip mapping, duplicate protection, request-number collisions/exhaustion, optimistic locking, missing-versus-stale failures, transactional events, rollback on a controlled publisher failure, idempotency, customer isolation, deterministic status pagination, UTC handling, InnoDB engines, and nested transaction rejection.

Every request uses `source = qa_fixture` and one unique `demo_marker`. A `finally` cleanup deletes events and snapshots for those request IDs before deleting the requests. The suite compares request/snapshot/event counts and a raw legacy user-meta hash before and after every run. Cleanup mismatch exits non-zero and reports the exact marker.

The suite must pass twice consecutively. The pure domain (`make test-buyback-domain`) and Phase 1A smoke (`make test-buyback`) suites remain separate real checks. Repository-wide `make test` and `make quality` still contain placeholder targets and are reported as such.

## Explicit non-goals

Phase 1B-B1 adds no public calculator, form, account replacement, operational admin UI, legacy import, price book, pricing, offer, inspection, payout, IBAN/IMEI, courier integration, notification, trade-in credit, or WooCommerce cart/order/checkout behavior. It changes no theme, frontend assets, product/order/user data, WooCommerce settings, inventory integration, or Számlázz.hu plugin.
